## 3. Архитектура: как рисовать и как объяснять

Схема на слайд (можно текстом или блоками):

```
┌───────────────────────────────────────────────┐
│  UI: 16 экранов (React Native компоненты)     │
│  Home · Catalog · Product · Cart · Checkout   │
│  Account · Orders · Wishlist · Reviews · Auth │
└───────────────────┬───────────────────────────┘
                    │ хуки / контексты
┌───────────────────▼───────────────────────────┐
│  Состояние: AuthContext · CartContext         │
│  (JWT-пользователь, гостевая корзина)         │
└───────────────────┬───────────────────────────┘
                    │ typed-функции
┌───────────────────▼───────────────────────────┐
│  API-слой: src/api/*                          │
│  client.ts · token.ts · media.ts · index.ts   │
└───────────────────┬───────────────────────────┘
                    │ HTTPS / JSON, Bearer JWT
┌───────────────────▼───────────────────────────┐
│  Backend: Perry.Api (.NET 8, PostgreSQL)      │
│  + Azure Auth Service (регистрация, вход)     │
└───────────────────────────────────────────────┘
```

Что говорить по слоям:

- **UI ничего не знает про HTTP.** Экраны вызывают `productsApi.list(...)`, `cartApi.add(...)`.
  Поменяется backend — правится один файл `src/api/index.ts`, а не 16 экранов.
- **Состояние — два контекста.** `AuthContext` держит пользователя и токен, `CartContext` —
  корзину. Они связаны: при входе корзина переезжает на пользователя.
- **API-слой — единственная точка выхода в сеть.** Внутри: базовый URL, заголовок
  `Authorization: Bearer`, разбор ошибок, типы ответов.

Почему так, а не «всё в экранах»: это тестируемо, это меняется в одном месте, это читается новым
человеком за вечер. Комиссия любит, когда студент может объяснить **границы** между слоями.

## 4. Обоснование технологий (самый частый вопрос)

Готовый ответ на 40 секунд:

> «Приложение нужно было на iOS и Android, сроки — учебные. Нативный стек — это два проекта на
> Swift и Kotlin, то есть двойная работа и двойные баги. Flutter дал бы то же самое, но команда
> уже писала десктоп на React и TypeScript, поэтому React Native переиспользует и язык, и модели
> данных, и часть логики API-слоя. Expo выбран потому, что он снимает ручную возню с нативными
> сборками: запуск на телефоне через Expo Go, конфигурация в `app.json`, сборка APK/AAB в облаке
> через EAS — без Xcode и Android Studio. При этом Expo не запирает: если понадобится нативный
> модуль, делается development build.»

Таблица для слайда «почему не …»:

| Вариант | Плюсы | Почему не взяли |
|---|---|---|
| Swift + Kotlin (нативно) | максимум производительности, полный доступ к API ОС | два кода, два разработчика, двойное время |
| Flutter | один код, быстрый UI | другой язык (Dart), нет переиспользования с десктопом на React |
| React Native без Expo | контроль над нативным слоем | ручная настройка Gradle/Xcode, дольше до первого запуска |
| **React Native + Expo** | один код, TypeScript, быстрый старт, EAS-сборки | ограничения Expo Go для нативных модулей (решено development build) |

Если спросят «а почему TypeScript, а не JavaScript»: типы ловят ошибки до запуска. У нас
`tsc --noEmit` проходит с нулём ошибок — это проверяемый факт, а не обещание.

## 5. Навигация

Что рассказать:

- **Два уровня.** Нижние вкладки — основные разделы (Home, Catalog, Cart, Account). Поверх —
  стек: карточка товара, оформление заказа, вход, регистрация, юридические страницы, заказы.
- **Почему так.** Вкладки — это «где я нахожусь», стек — «куда я провалился». Пользователь всегда
  может вернуться назад одной кнопкой.
- **Deep links.** Схема `perry://`, например `perry://product/{id}` — ссылка на товар открывает
  приложение сразу на карточке. На web те же адреса работают как обычные URL
  (`/catalog`, `/cart`, `/product/:id`), поэтому страницу можно переслать.
- **Один навигатор на всё приложение.** `NavigationContainer` один, конфигурация путей — в
  `src/navigation/RootNavigator.tsx`.

Сильный аргумент для защиты: **web-версия и мобильная — один и тот же код**, различается только
навигационная оболочка. Это экономия и единообразие UX.

## 6. API-слой и работа с ошибками

Рассказывать так:

> «Все запросы идут через один `apiFetch`. Он сам подставляет базовый адрес, добавляет
> `Authorization: Bearer`, парсит JSON, а на не-2xx бросает типизированную `ApiError` со статусом
> и телом. Поэтому экран не разбирает ответ вручную — он ловит одно исключение и показывает
> сообщение. Отдельно обработан сетевой сбой: пользователю объясняют не «Network request failed»,
> а что именно недоступно и что делать — например, что телефон и компьютер должны быть в одной
> Wi-Fi сети.»

Что важно упомянуть:

- **Две базы адресов.** Product API и Auth Service — разные сервисы, у них разные хосты, поэтому
  в клиенте есть параметр `base: "product" | "auth"`.
- **Разбор ошибок бэкенда.** `ProblemDetails` от .NET, поля `errors`, `title`, `message` — всё
  сводится к одной человекочитаемой строке (`formatApiErrorMessage`).
- **401 — это не «ошибка», а сигнал.** Если сервер ответил 401, токен протух: сессия сбрасывается,
  пользователь отправляется на вход. Без этого приложение показывает пустые экраны и молчит.

## 7. Авторизация: как устроено и как объяснять

Схема на слайд:

```
Регистрация (3 шага):
  e-mail + пароль  →  Auth Service присылает код  →  ввод кода  →
  complete-registration  →  login  →  JWT

Вход:
  login + пароль  →  Auth Service  →  JWT  →  SecureStore  →  все запросы с Bearer

Старт приложения:
  есть токен?  →  GET /auth/me  →  ок: показываем пользователя
                              →  401: чистим токен, показываем гостя
```

Ключевые тезисы:

1. **Пароли приложение не хранит вообще.** Их принимает Auth Service и возвращает только токен.
   Это правильный ответ на вопрос «а как вы храните пароль?» — «никак, и это осознанно».
2. **Токен — в защищённом хранилище.** `expo-secure-store` — это Keychain на iOS и Keystore на
   Android. На web — `localStorage`, потому что SecureStore там нет; это осознанный компромисс
   для отладочной web-версии.
3. **Регистрация многошаговая**, потому что так требует сервис: сначала создаётся заявка, потом
   подтверждается e-mail кодом, и только затем выдаётся JWT. В приложении это три экрана
   (`Register` → `SendCode` → вход).
4. **Восстановление пароля** — отдельный экран, код приходит на почту.
5. **Сессия восстанавливается при старте**: приложение не заставляет логиниться заново после
   перезапуска.

Если спросят «почему не OAuth/соцвход»: это следующий шаг, архитектура готова — достаточно
добавить провайдера в Auth Service.

## 8. Три технических решения, которые стоит продать на защите

Именно они отличают «сделал экраны» от «сделал приложение». Рассказывайте про них с деталями.

### 8.1. Гостевая корзина со слиянием при входе

Проблема: человек добавляет товары до регистрации. Если корзина живёт только на сервере с
привязкой к пользователю — у гостя её нет.

Решение: при первом запуске генерируется UUID сессии и сохраняется на устройстве. Корзина
работает по этому `sessionId` — гость может всё: добавить, изменить количество, удалить,
оформить заказ. При входе вызывается `POST /cart/merge`: серверная корзина пользователя
объединяется с гостевой, гостевая очищается. Повторный merge защищён ref-ом, чтобы не сработал
дважды.

Что сказать: «Мы не теряем товары, которые человек выбрал до входа. Это самая частая точка, где
интернет-магазины теряют конверсию».

### 8.2. Один код — два транспорта: web через прокси, телефон напрямую

Проблема: на web браузер запрещает запросы к другому origin (CORS), а на телефоне `localhost` —
это сам телефон, а не компьютер разработчика.

Решение:

- **Web.** Metro-сервер приложения проксирует `/api` на Product API и `/auth-api` на Auth Service.
  Для браузера всё same-origin — CORS не возникает вообще. Настраивается в `metro.config.js`.
- **Native.** Адрес API вычисляется в рантайме (`src/api/productOrigin.ts`): если в `.env`
  указан `localhost`, приложение берёт **IP компьютера из hostUri Metro** и подставляет его вместо
  loopback. Для Android-эмулятора есть fallback `10.0.2.2`.

Что сказать: «Мы решили это не костылём в виде ручного IP в каждом файле, а одним модулем, который
сам понимает, где он запущен. Разработчику достаточно `npm start`».

Это отличный ответ на вопрос «почему у вас на телефоне не работает, а на компьютере работает».

### 8.3. Изображения товаров

Проблема: картинки приходят и абсолютными URL (внешний CDN), и относительными (`/uploads/...`).

Решение (`src/api/media.ts`): относительные достраиваются до нужного origin — на web остаются
относительными (их отдаёт прокси), на телефоне получают LAN-адрес API. Для внешних CDN, которые
запрещают hotlink, на web используется прокси-ресайз (`wsrv.nl`) с приведением к 640×640.

Что сказать: «Мы не правили данные в базе под мобильное приложение — клиент адаптируется к тому,
что уже отдаёт сервер».

## 9. Демо: сценарий на 3 минуты

Порядок проверенный — от простого к сложному, с обязательной точкой «вау» в середине.

| Шаг | Действие | Что подчеркнуть |
|---|---|---|
| 1 | Главная | категории и блок «Trending deals» пришли с API, а не зашиты в код |
| 2 | Каталог: фильтры и сортировка | параметры уходят на сервер, пагинация по 20 |
| 3 | Карточка товара | галерея, рейтинг, цена со скидкой, кнопка «в корзину» |
| 4 | **Добавить в корзину без входа** | «корзина уже работает, хотя пользователь — гость» |
| 5 | Войти (заранее подготовленный аккаунт) | «корзина слилась с серверной — товары не потерялись» |
| 6 | Оформление заказа → «Мои заказы» | заказ реально создан на сервере |
| 7 | Переключиться на web-версию | «тот же код, тот же аккаунт, те же заказы» |
| 8 | Открыть `perry://product/{id}` | deep link ведёт на карточку |

Правила демо:

- **Подготовьте данные заранее.** Аккаунт с паролем, товар с картинками, товар «нет в наличии».
- **Ничего не вводите вживую дольше 5 секунд.** Пароль — копипастом или короткий.
- **Интернет обязателен** — авторизация идёт в облачный сервис. Не полагайтесь на Wi-Fi вуза:
  сделайте локальную точку доступа с телефона, если что.
- **Записанное видео — страховка.** 90 секунд экрана, если что-то отвалится.
- Если демо упало — не оправдывайтесь долго. Одна фраза: «сервер недоступен, покажу по записи»,
  и продолжайте.

## 11. Ограничения — говорите сами, это плюс

Комиссия ценит честность и умение видеть границы решения. Скажите примерно так:

> «Что сознательно не сделано в этой версии:
> — офлайн-режим и кэш каталога: нужен локальный слой хранения и стратегия синхронизации;
> — push-уведомления: требуют нативной настройки и серверной части;
> — оплата: интеграция платёжного провайдера и PCI-требования — отдельная задача;
> — автоматические тесты UI: сейчас проверки статические (типы, конфиг, сборка) плюс ручной
> сценарий; следующий шаг — Detox или Maestro для сквозных сценариев.
> Всё это не влияет на основную бизнес-логику, которая работает end-to-end.»

Никогда не говорите «мы не успели» — говорите «сознательно вынесено за рамки, потому что…».

## 12. Вопросы комиссии и готовые ответы

**1. Почему React Native, а не нативная разработка?**
Один код на две платформы, переиспользование TypeScript и моделей данных с десктопной версией,
сроки. Производительности хватает: тяжёлая работа на сервере, UI — списки и формы.

**2. Чем Expo лучше обычного React Native?**
Готовый набор нативных модулей, конфигурация вместо ручной правки Gradle и Xcode, запуск на
телефоне без сборки (Expo Go), облачные сборки APK/AAB через EAS. Ограничение — кастомные
нативные модули требуют development build; у нас таких нет.

**3. Где хранится токен и почему это безопасно?**
`expo-secure-store` — Keychain/Keystore, шифрование на уровне ОС. В коде и репозитории токенов и
секретов нет, `.env` в git не попадает.

**4. Что происходит, когда токен истекает?**
Сервер отвечает 401, клиент сбрасывает сессию и показывает гостя; пользователь входит заново.
Прозрачное обновление токена — следующий шаг, на backend есть `/auth/refresh`.

**5. Как приложение узнаёт адрес сервера?**
Web — через прокси Metro, same-origin. Native — из `.env`, а если там `localhost`, то IP
компьютера подставляется из данных Metro автоматически; для эмулятора Android — `10.0.2.2`.

**6. Почему на телефоне не работает `localhost`?**
`localhost` — это сам телефон. Компьютер с API доступен по IP в локальной сети, и API должен
слушать не только loopback, а все интерфейсы (`0.0.0.0`).

**7. Как вы решали CORS?**
На web запросы идут на тот же origin, их проксирует Metro-сервер (`/api`, `/auth-api`) — браузер
не видит кросс-доменного запроса. На native CORS не применяется, там прямой запрос по HTTP.

**8. Что будет, если сервер недоступен?**
Пользователь видит понятное сообщение, а не техническую ошибку: что именно недоступно и что
проверить. Экраны не падают — обработаны и сетевой сбой, и не-2xx ответ.

**9. Как обеспечена производительность списков?**
`FlatList` с ключами и пагинацией по 20, мемоизация коллбеков, лёгкие карточки, изображения
приводятся к разумному размеру. Каталог на 207 товарах листается без рывков.

**10. Как тестировали?**
Три уровня: статические проверки (`tsc --noEmit` — 0 ошибок, `expo-doctor` — 21/21), сборка
бандла (`expo export`), ручной сквозной сценарий на web, Android и iOS: каталог → корзина → вход →
заказ. Плюс проверка API через Swagger.

**11. Чем мобильная версия отличается от десктопной?**
Тот же backend и та же бизнес-логика. Отличается UI: нижние вкладки вместо бокового меню,
крупные тач-зоны, вертикальные списки, карточка товара на весь экран. Данные общие — один аккаунт,
одна корзина, одни заказы.

**12. Сколько человек писали и что делали вы?**
Отвечайте честно и конкретно: какие модули ваши. «Я делал мобильный клиент: API-слой, контексты
авторизации и корзины, экраны каталога и оформления заказа, настройку сборки».

**13. Как собирается релиз?**
`eas build --profile preview` — APK для теста, `--profile production` — AAB для Google Play.
Профили описаны в `eas.json`, версия и иконки — в `app.json`.

**14. Что дальше?**
Офлайн-кэш каталога, обновление токена без повторного входа, push-уведомления о заказах,
сквозные UI-тесты, оплата.

**15. Если не знаете ответ.**
Не выдумывайте. «В этой версии не реализовано, вижу два варианта решения — через X или через Y,
выбор зависит от Z». Комиссия проверяет не всезнание, а инженерное мышление.

## 13. Чего не говорить

| Не говорите | Почему |
|---|---|
| «Мы написали backend» | Backend — отдельный сервис команды, вы писали клиент. Не приписывайте чужое: поймают одним вопросом. |
| «Это нативное приложение» | Оно кроссплатформенное на React Native. Терминология важна. |

| «Не знаю, это не я делал» | «Этим занимался коллега, я знаю на уровне интеграции: вот как это стыкуется с моим кодом». |
